# Authorized Integration Map — Drive Artifact Intake

**Author:** Manus AI  
**Decision date:** 2026-09-11  
**Scope:** This map classifies the identified Google Drive artifacts for an original, clean-room game project. It is an intake-control document, not a license determination or approval to copy, compile, distribute, or execute any artifact.

## Decision summary

The Drive corpus does **not** establish ownership or a release-ready 2006Scape product. Folder names, archive names, successful extraction, duplicate hashes, and compilation results are not ownership evidence. Until the required written chain of rights and a technical/supply-chain review are complete, the corpus remains outside the product runtime path, Git history, CI runners, build contexts, and release artifacts.[1]

Three handling statuses apply:

| Status | Meaning | Permitted now | Prohibited now |
|---|---|---|---|
| **Read-only evidence** | Material may inform provenance, compatibility, or licensing review. | Record ID, metadata, hash, access date, and a narrowly scoped review conclusion. Read static text in an access-controlled evidence store. | Importing text, configuration, code, brand assets, protocols, dependencies, or credentials into product source or runtime paths. |
| **Candidate for authorized integration** | The item is a possible future source input, not an approval. | Isolated, non-executing source/license/security review after an artifact-specific written authorization is received. | Compilation, execution, derivative development, redistribution, production use, or combining with another corpus component before every gate passes. |
| **Quarantined** | The item is mixed, executable, proprietary-risk, content-bearing, or insufficiently attributable. | Preserve the identifier and cryptographic evidence; perform only a legally authorized, isolated forensic review if needed. | Running, unpacking into a project tree, importing, publishing, building against, redistributing, or using it as a launcher/client/cache/map/protocol input. |

> **Default rule:** An unknown Drive child, a future upload into a named folder, or a duplicate/revision not specifically cleared is **quarantined by default**. A folder label such as `Server`, `Client`, `Cache`, `Build`, or `Companion` never grants rights.

## Cross-artifact authorization gate

An item can move only from **candidate** to **approved for a stated, limited use**. The approving record must identify the exact Drive ID, immutable SHA-256, version/revision, intended use, and approval date. It must include all evidence below; a positive answer for one component does not clear a related archive, folder, binary, map, client, or document.

| Required evidence | Minimum acceptable record | Gate owner | Immediate stop condition |
|---|---|---|---|
| **Identity and integrity** | Drive ID, parent path as observed, MIME type/size, acquisition date, SHA-256 of the retrieved bytes, and a retained copy in evidence storage. MD5 duplicate groups are traceability only. | Intake custodian | The bytes differ from the reviewed hash, the ID cannot be resolved, or the file contains unexpected nested archives/binaries. |
| **Authority chain** | Signed or otherwise verifiable statement from the actual rights holder naming the item ID/hash and the grantor’s authority. Access to Drive, a shared link, a filename, or an uploader name is insufficient. | Legal/provenance reviewer | No identified rights holder, conflicting claims, unverifiable authority, or an authorization that names only a folder/repository rather than the exact artifact. |
| **Rights scope** | Express rights to copy, modify, compile, integrate, distribute, sublicense if needed, and use commercially; territory, duration, attribution, source-offer/copyleft, and contributor obligations. | Legal reviewer | Any excluded use conflicts with the planned use, the term/territory is insufficient, third-party notices are missing, or counsel flags legacy-game/IP risk. |
| **Third-party and creative provenance** | Dependency lockfiles/notices/SBOM where applicable; asset register for art, audio, fonts, maps, names, and contributor attestations. | Engineering + legal | Unknown dependency or asset origin, incompatible license, copied publisher material, undisclosed generated content restrictions, or missing contributor assignment/permission. |
| **Technical and security review** | Isolated static analysis, secret/malware/license scan, dependency review, reproducible build evidence where relevant, and a scope-specific compatibility test using synthetic/original fixtures only. | Security + engineering | Live credentials, private keys, suspicious code, execution-only proof, proprietary client/cache/protocol linkage, unsupported license, or unreviewed binary payload. |
| **Release governance** | Written approval naming allowed use (for example, “internal source reference only” or “ship as dependency”), reviewer, decision date, and revocation/contact process. Shipped items also need SBOM and signed provenance. | Release owner | Approval is oral, blanket, expired, ambiguous, unauditable, or the planned use changes. |

A validated authorization permits **only the named scope**. “May integrate” below means that an item may enter this gate; it does not mean it is presently usable. Any artifact that includes an official/proprietary client, cache, game data, publisher protocol implementation, credentials, anti-cheat bypass capability, or unlicensed brand/content is ineligible for integration irrespective of technical quality.[2]

## Practical intake checklist

Use this checklist for **one Drive ID at a time**. The required outcome is a recorded status, not a forced integration decision.

| Step | Intake action | Required record | Safe outcome | Mandatory stop condition |
|---|---|---|---|---|
| 1. Identify | Record exact Drive ID, title, MIME type, size, observed parent, access date, and requestor. | Intake ticket and immutable evidence row. | Continue only with an exact ID. | Request refers only to a filename, folder, screenshot, or “the latest version.” |
| 2. Freeze evidence | Retrieve to access-controlled evidence storage only when authorized to do so; calculate SHA-256; retain original metadata and read-only copy. | SHA-256, retrieval log, chain-of-custody location, and any existing MD5. | Classify as read-only evidence or proceed to rights review. | Hash/metadata cannot be reproduced; content differs from the reviewed record; nested executable/archive scope is unknown. |
| 3. Triage content without execution | Identify source, binary, archive, configuration, documentation, asset, map/cache, protocol, dependency, credential, and branding indicators. | Content manifest and risk flags. | Documentation may remain evidence; source-like material may become a candidate. | Any executable, client/cache/map payload, secret, protocol implementation, or prohibited tool appears without prior scope approval. |
| 4. Verify rights holder | Obtain an artifact-specific ownership/license statement from the rights holder, with grantor authority. | Signed clearance linked to Drive ID and SHA-256. | Continue only if scope covers intended use. | Drive access, contributor name, repository link, or document language is offered instead of a rights chain. |
| 5. Verify scope and third parties | Confirm copying, modification, compilation, distribution, commercial/sublicense rights; inspect dependencies and creative assets separately. | License matrix, notices, SBOM/lockfile, contributor/asset register. | Candidate can enter isolated technical review. | Any missing third-party rights, incompatible terms, unclear asset provenance, or legacy publisher content. |
| 6. Run isolated technical review | Scan statically for malware/secrets/licenses; review code/dependencies; test only with synthetic/original inputs; document outputs. | Scan reports, review sign-off, reproducible build evidence if relevant. | Approve only the narrowly reviewed component and use. | Live secret, suspicious behavior, prohibited client/cache/protocol relationship, unreviewed binary, or irreversible content transformation. |
| 7. Make the release decision | Record approved use, exclusions, approver, date, expiry/re-review trigger, and revocation contact. | Signed provenance/release record, SBOM, manifest entry. | Permit only stated use in an allowlisted repository path. | Approval is blanket/ambiguous/expired, build inputs differ, or planned use expands. |
| 8. Enforce continuously | CI verifies allowed IDs/hashes and rejects prohibited names/assets, unsigned content, incomplete provenance, or unauthorized changes. | Review-status register and CI logs. | Ship only approved, project-owned/licensed outputs through signed release controls. | Any deviation from the approved hash/scope, failed provenance gate, or discovery of a rights/security issue. |

Maintain the following fields outside the product runtime path. The project’s initial register should start with the listed IDs and mark every non-cleared item as `evidence-only`, `candidate-pending`, or `quarantined`.

## Implementation constraints

The immediate authorized work is a clean-room original platform using synthetic/original fixtures and a new protocol. The Drive inventory may support evidence and licensing review only. A future approved launcher must install only project-owned or expressly licensed artifacts, verify signed update metadata and exact artifact hashes, and reject untrusted or stale releases; it cannot cure rights defects in a downloaded payload.[1] [2]
